# Лісовий секретар

## Що це

Telegram-бот «Лісовий секретар» для звірів із восьми рукавичок. Він відповідає лише за документами «Лісового архіву» й порадами, які надсилають самі звірі, і щоразу називає джерело. Відповіді пише `openai/gpt-oss-120b` на безкоштовному рівні Groq; пошук, вибір місця й список джерел бот робить сам, без LLM.

## Спробуйте

Приклади з gold-набору ([docs/gold-questions.md](docs/gold-questions.md)):

- **T18** «Які гриби біля сосон?» — бот застосовує Карту лісу: «У соснах» належить хвойному лісу, тож відповідь із «Грибного путівника хвойного лісу».
- **T04** «Чим утеплити рукавичку під вербою?» — «Під вербою» належить і листяному лісу, і річці: бот показує обидві поради, каже, що вони різняться, і не вибирає.
- **T02** «Коли треба утеплювати рукавичку?» — місце не назване: короткі варіанти для кожної частини лісу і кнопки рукавичок.
- **T19 → T20** «Коли збори мешканців?», потім «У соснах» — у кожної рукавички свої збори, тож бот перепитує рукавичку, а друга репліка уточнює перше питання.
- **T05** «Коли Ведмідь лягає в сплячку?» — порада рукавички Ведмедя (У ліщині) важливіша за загальний Календар.
- **T22** «Коли прилітають лелеки?» — в архіві цього немає, і бот так і каже.
- **Порада файлом** — надішліть PDF, DOCX або TXT: бот спитає ваше ім'я (лише вперше), визначить місце або попросить вибрати його кнопками і, якщо схожа порада вже є, спитає, чи це її нова версія.

## Запуск

Потрібні Docker і Docker Compose v2.

1. **Токен бота:** у Telegram напишіть @BotFather → `/newbot` → скопіюйте токен.
2. **Ключ Groq:** console.groq.com → API Keys → Create API Key. Безкоштовно.
3. Скопіюйте налаштування й впишіть у `.env` обидва значення, `TELEGRAM_BOT_TOKEN` і `GROQ_API_KEY`:

   ```bash
   cp .env.example .env
   ```

4. Запустіть:

   ```bash
   docker compose up --build
   ```

Під час першого старту Docker збирає образ (Python і tesseract з українською мовою для OCR сканів), бот застосовує міграції й імпортує 78 документів архіву з `data/archive/`. Повторний старт пропускає вже імпортовані файли.

Бот готовий, коли в лозі є рядок `Run polling for bot @…`:

```bash
docker compose logs bot
```

Один токен — один запущений бот. Якщо той самий токен уже працює деінде, Telegram віддає кожне оновлення лише одному з них, і бот відповідатиме через раз.

### Змінні `.env`

| Змінна | За замовчуванням | Що робить |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | — | Токен від @BotFather. Обов'язкова. |
| `GROQ_API_KEY` | — | Ключ Groq. Обов'язкова. |
| `GROQ_MODEL` | `openai/gpt-oss-120b` | Модель відповідей. |
| `GROQ_REASONING_EFFORT` | `low` | Токени міркувань теж ідуть у ліміт за хвилину; `medium` не покращив виконання інструкцій (див. «Відомі обмеження»). |
| `GROQ_FALLBACK_MODEL` | порожньо | Друга модель на випадок 429. Порожньо — чекати й повторювати основною: `openai/gpt-oss-20b` частіше губить застереження. |
| `GROQ_MAX_COMPLETION_TOKENS` | `512` | Стеля відповіді разом із міркуваннями. Groq бронює її в ліміті ще до відповіді, тож зайве з'їдає ліміт. |
| `DIALOGUE_TTL_SECONDS` | `900` | Скільки бот пам'ятає попереднє питання, щоб прийняти «У соснах» як уточнення. |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | `lisovyi` | База в контейнері `db`. Назовні вона не відкрита. |

## Ліміти безкоштовного Groq

- Для `openai/gpt-oss-120b` на момент розробки: 8K токенів за хвилину і 200K за добу.
- У повному прогоні gold-набору перед здачею (31 питання, 28 викликів моделі) один виклик у середньому коштував 3 705 токенів: 3 504 prompt і 201 completion.
- Groq бронює в ліміті за хвилину `prompt + max_completion_tokens` ще до відповіді: ≈ 3 504 + 512 = 4 016 токенів на питання. Тому стеля відповіді — 512 токенів, а не більше.
- Звідси ~2 питання за хвилину (8 000 / 4 016) і ~50–54 за добу на один ключ: 200 000 / 4 016, якщо добовий ліміт рахує бронь, або 200 000 / 3 705, якщо фактичні токени.
- Бот звертається до Groq по одному запиту. Якщо ліміт вичерпано, звір один раз бачить «Зараз у мене багато питань, відповім за хвилинку 🌿», а питання чекає своєї черги до 30 секунд. Якщо чекати довше або Groq двічі поспіль відповів 429, бот просить спитати за хвилину. У gold-прогоні так сталося з одним питанням із 31 (T23).

### Технічні рішення без питань до замовниці

- `.doc` не підтримується: бот просить зберегти як `.docx`;
- на фото й інші формати бот ввічливо пояснює, які формати приймає;
- скановані PDF від звірів проходять той самий OCR, що й архівні.

## Суперечності в архіві і як бот їх розв'язує

У дужках — питання gold-набору, які їх перевіряють ([docs/gold-questions.md](docs/gold-questions.md)).

1. **Утеплення** (T01, T02, T21). Календар каже «у листопаді», хвойний ліс — «у жовтні», листяний — «коли облетить листя, до першого снігу». Для хвойного лісу бот відповідає «у жовтні» і може згадати Календар як загальну пораду.
2. **Сплячка** (T05, T06). Календар каже «у грудні», а Ведмідь (У ліщині) і Їжак (На узліссі) лягають з листопада. Порада рукавички головніша.
3. **Брід** (T07). Біля річки брід вище греблі безпечний, коли гребля відкрита і вода спала. Для «Біля бобрової греблі» вбрід ніколи, тільки по греблі. Перемагає порада рукавички.
4. **Горіхи й жолуді** (T09, T11). Підсумок Календаря «у жовтні — жолуді й горіхи» суперечить його ж тексту. Бот спирається на окрему пам'ятку: горіхи з кінця серпня, жолуді з середини вересня до кінця жовтня.
5. **Під вербою** (T04, T12). Гриби: на 4–5 день після дощу (листяний ліс) або наступного дня (річка). Утеплення: дубове листя або очерет на корінні. Бот показує обидва варіанти і не вибирає (вимога 8).
6. **Дощ біля річки** (T13). Після сильного дощу до берега два дні не підходити, а опеньки йдуть наступного дня після невеликого дощу. Бот має сказати обидва.
7. **Вечір під дубом** (T14). Восени ввечері під дубами не ходити через кабанів, а гостей у «Під дубом» приймають тільки ввечері. Бот дає правило рукавички, показує застереження і каже, що поради різняться.
8. **Мисливці на просіці** (T15, T27). Маршрут «Під ялиною → до дуба через просіку» не має застереження, а «Під дубом» каже: просікою по суботах ходять мисливці. Бот додає застереження до маршруту.
9. **Зайчик і вирубка** (T16). У соснах кора осик на вирубці — для Зайчика, але вночі на вирубці полює пугач. Бот каже обидва.
10. **Сигнали Сороки** (T17). Три короткі крики — мисливці, для всього лісу. Скрекоче двічі — чужий звір, лише У ліщині. Бот дає загальну відповідь і згадує виняток.
11. **«Які гриби біля сосон?»** (T18). У «У соснах» немає грибної пам'ятки, тож через Карту лісу відповідь береться з «Грибного путівника хвойного лісу».

Знайдено пізніше, під час збирання gold-набору:

- **T10** — горіхи в соснах: пам'ятка листяного лісу там не діє, і бот її не застосовує.
- **T28** — гриби на узліссі: грибні путівники частин лісу там не діють, бо узлісся не належить жодній частині.

## Рішення, яких вимоги прямо не задають

- **T05, T14, T17, T23** — див. розділ «Рішення розробника» в [docs/gold-questions.md](docs/gold-questions.md).
- **Скани архіву.** 19 сканів мають вивірені вручну транскрипти в `data/transcripts/`, прив'язані до sha256 файлу. OCR спрацьовує, лише якщо файл змінився, і для нових сканів: на фоні «береста» він плутає цифри («350 кроків» → «850»).
- **«Поганий зір».** Числа з нового скану бот перепитує кнопками. Якщо вони неправильні, бот просить .docx або .txt.
- **Місце нової поради.** Спершу правила (назва, вступне речення, рукавичка в лапках), а якщо вони не спрацювали — кнопки. Без LLM.
- **Видалення.** Видалення поради, яка замінила іншу, повертає замінену. Видалення не стирає знання з архіву.
- **Вимога 8 детерміновано.** Чи є конфлікт, вирішує детектор. Модель лише заповнює окремий пункт для кожної частини, а вступ і «Оберіть ту, що підходить саме вашому місцю» пише бот.
- **Звертання на «ви».** На «ти» модель уперто зісковзувала на «ви», тож увесь бот перейшов на «ви».
- **Джерела будує бот.** Модель повертає номери документів, назви підставляє бот. Вигадане джерело неможливе.

## Як перевірено

**Тести.** Тести з базою працюють з окремою базою з `DATABASE_URL` і щоразу створюють її наново:

```bash
set -a; . ./.env; set +a
docker compose run --rm \
  -e DATABASE_URL="postgresql+asyncpg://$POSTGRES_USER:$POSTGRES_PASSWORD@db/lisovyi_test" \
  bot pytest -q -rs
```

Перед здачею: 668 тестів пройшли, 0 пропущено, за 12 хв 51 с на ноутбуці розробника. Telegram у тестах замінено записом запитів, Groq — фейком; базу дає PostgreSQL з контейнера `db`.

**Gold-набір.** 31 питання з очікуваною поведінкою, документами, що мають бути серед джерел, і тим, що відповідь має й не має сказати: [docs/gold-questions.md](docs/gold-questions.md). Прогін по справжньому Groq:

```bash
docker compose stop bot
docker compose run --rm -v "$PWD:/app" bot python scripts/run_gold.py
docker compose start bot
```

Бота варто зупинити, щоб він не ділив з прогоном ліміт за хвилину. Повний прогін перед здачею: вид відповіді збігся з очікуваним у 28 з 31 питань, усі обов'язкові джерела були серед джерел відповіді в 26 з 31. Витрачено 103 748 токенів (98 115 prompt і 5 633 completion), ≈52% добового ліміту, за 11 хвилин. Розбіжності: T13 і T11 описано в «Відомих обмеженнях», T23 — у «Лімітах безкоштовного Groq».

Скрипт перевіряє лише вид відповіді й джерела. Зміст відповідей перевірено вручну за полями «Має сказати» / «Не має» gold-набору, і саме так знайдено обмеження нижче.

## Відомі обмеження

Виявлено вручну в живих прогонах gold-набору. Вони пережили дві версії промпту й `reasoning_effort=medium`. Наступний крок — модель, що краще тримає інструкції, але на безкоштовному Groq такої немає.

- **Злиття порад для різних випадків.** T08: до переправи по камінню біля верби модель додає умову броду вище греблі («переконайтеся, що бобри відкрили греблю»).
- **Власні висновки.** T26: «до першого снігу — це зазвичай листопад».
- **Неточні дієслова й прийменники.** T10: «падають» замість «збирають»; T27: «на північ» замість «на півночі».
- **Загальна порада часом випадає** (T07, T17), хоча документ є в джерелах.
- **Узагальнення адресата.** «Що їсти під вербою?» → «можна їсти комарів і мошки», хоча в записі це частування для Жабки й Горобця.
- **Дрібні домисли в переказі** («берег, затоплений під час дощу» замість «берег, який заливало»).
- **Хибне «немає в записах».** T13: обидва потрібні документи («Грибний путівник біля річки» і «Небезпеки біля річки») були в контексті, а модель відповіла, що інформації немає.
- **Застереження з іншого документа губиться.** T15: маршрут «Під ялиною → до дуба» через просіку без суботнього застереження про мисливців, хоча документ «Під дубом» був у контексті.
- **Варіанти за частинами не завжди.** T11: на «Коли збирати горіхи?» модель дала лише пораду листяного лісу, без варіантів для інших частин.
- **Помилки в словах.** T28: «кри́льце на ніжці» замість «кільце»; «запитайте у Їжак».
- **Ліміти безкоштовного Groq:** ~50–54 питання на добу на один ключ і ~2 за хвилину (див. «Ліміти безкоштовного Groq»).
- **OCR нових сканів** плутає цифри. Тому бот перепитує числа, але текст поза числами не перевіряє.

Що гарантовано попри це:

- джерела завжди справжні;
- «не знайдено» й перепитування рукавички детерміновані;
- поради з іншого місця в контекст не потрапляють: 45 з 45 кейсів пошуку (`tests/test_retrieval_cases.py`).

## Що далі

- Фільтр сповіщень за місцем (вимога 18, відкладено).
- Модель, що краще тримає інструкції, коли вона з'явиться на доступному рівні Groq.
- Одна таблиця назв частин лісу: зараз назви й відмінки частин лісу описано в кількох модулях.
- Шаблонна БД для тестів: зараз кожен тест з базою створює її наново й проганяє міграції, тож повний прогін триває ~13 хвилин.

## Архітектура

- `ingest/` читає PDF, DOCX, TXT і скани, класифікує документи за місцем і імпортує архів.
- `search/` розпізнає місце за чинною Картою і збирає контекст BM25 за шарами «рукавичка → частина → весь ліс».
- `answer/` питає Groq зі strict JSON-схемою, перевіряє відповідь і будує список джерел.
- `uploads/` приймає поради звірів: текст, місце, нова версія чи окрема порада.
- `notify.py` розсилає сповіщення підписникам, `bot/` — тонкий шар aiogram.
- Дані — PostgreSQL: документи зі статусами `active` / `replaced` / `deleted`, звірі, підписки, Карта лісу.

Докладно, зі шляхом питання й поради та числами за рішеннями: [docs/architecture.md](docs/architecture.md).
